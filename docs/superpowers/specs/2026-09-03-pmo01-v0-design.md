# PMO01 V0 — Learning Prototype Design

## Purpose

Build a minimal, content-first prototype for an advanced Project Management course focused on systems thinking, flow, uncertainty, and decision quality rather than PM ceremonies or tool usage.

The V0 exists to validate the learning format before building a larger platform or producing the full course.

## Product goal

A learner should be able to open the site, study one coherent module, make decisions in realistic scenarios, complete a boss case, and see lightweight local progress.

Success is not "the learner opened every page". Success is that the format makes it easier to diagnose a project and explain a better management decision.

## V0 scope

The first vertical slice contains:

- A typographic, editorial homepage.
- One module: `FLOW`.
- Four lesson placeholders that can later be filled with validated content:
  1. Local optimization.
  2. Queues.
  3. Utilization.
  4. Bottlenecks.
- One reusable Decision Drill interaction.
- One module-level boss case.
- Lightweight local progress.
- Previous/next lesson navigation.
- Responsive desktop/mobile layout.
- Static deployment through GitHub Pages.

The V0 intentionally validates the platform with one module only. Full course content is out of scope.

## Learning architecture

Each lesson follows this internal instructional sequence:

1. Principle.
2. Mental model.
3. Why conventional wisdom fails.
4. Mechanism.
5. Example.
6. Failure pattern.
7. Decision drill.
8. Application prompt.

The UI does not need to expose these as separate cards or tabs. The lesson should read as a continuous editorial document.

The module ends with a boss case that requires the learner to diagnose a realistic delivery system and choose an intervention.

## Visual direction

Use typographic editorial minimalism.

The interface should feel closer to a well-designed book, technical essay, or long-form publication than to an LMS dashboard.

Principles:

- Content is the dominant visual element.
- Narrow reading measure, approximately 65–75 characters per line.
- Strong typographic hierarchy.
- Generous vertical rhythm.
- Light background and near-black text by default.
- One restrained accent color at most.
- No gradients, glassmorphism, decorative dashboards, large progress bars, confetti, XP, coins, leaderboards, or visually noisy cards.
- Borders, shadows, and rounded corners are used only where interaction clarity requires them.
- Learning diagrams are allowed when they improve reasoning, not as decoration.

## Gamification model

V0 uses quiet gamification only.

Lesson states:

- `unseen` — not opened/completed.
- `studied` — learner explicitly marks the lesson as studied.
- `mastered` — reserved for later evidence-based logic; V0 may display the state but must not automatically assign it from page visits.

Visual notation may use restrained symbols such as:

- `○` unseen
- `◐` studied
- `●` mastered

V0 may include a module-completion milestone after the boss case, but no generic achievement engine is built.

## Technical approach

### Framework

Use Astro with TypeScript.

Rationale:

- Static output matches GitHub Pages.
- Content-first architecture.
- Minimal client JavaScript.
- Markdown support.
- Easy separation between editorial content and interactive islands.

### Content

Use Markdown-first content.

Do not make MDX the default. Introduce MDX only if an interactive lesson requires an embedded component and plain Markdown cannot express it cleanly.

Lesson metadata should remain minimal in V0:

```yaml
id: queues
title: Queues
module: flow
order: 2
```

Avoid building a generalized ontology, knowledge graph, skill taxonomy, or prerequisite engine in V0.

### Styling

Use vanilla CSS with custom properties.

No Tailwind, CSS-in-JS, component library, or external design system.

Suggested style files:

- `src/styles/tokens.css` — color, spacing, typography tokens.
- `src/styles/typography.css` — editorial reading rules.
- `src/styles/global.css` — layout and global behavior.

### Progress

Store learner state in browser `localStorage`.

V0 does not include:

- accounts;
- server persistence;
- cross-device sync;
- progress migrations;
- a generalized repository abstraction.

Progress code should still be isolated in one small module so direct storage calls do not spread through UI components.

Example state shape:

```ts
type LessonState = 'unseen' | 'studied' | 'mastered';

type ProgressState = Record<string, LessonState>;
```

### Interaction

Use client-side JavaScript only for behavior that cannot be static:

- marking progress;
- revealing/recording Decision Drill choices;
- small boss-case interactions if required.

Everything else should render as static HTML.

## Homepage

The homepage acts as a table of contents rather than a dashboard.

It should communicate:

- course title;
- one-sentence promise;
- module list;
- lesson titles;
- subtle progress state.

V0 may show future modules as text-only placeholders, but only `FLOW` is implemented.

## Lesson page

A lesson page contains:

- module + lesson index;
- title;
- short opening thesis;
- editorial body;
- optional decision drill;
- mark-as-studied control;
- previous/next navigation.

No persistent sidebar is required in V0.

## Decision Drill

The Decision Drill is the only required reusable interactive learning component in V0.

Behavior:

1. Present a realistic PM situation.
2. Present a small set of plausible actions.
3. Learner selects one action.
4. Reveal analysis explaining consequences and trade-offs.
5. Do not use celebratory correctness UI.

The goal is decision quality and reasoning, not trivia scoring.

## Boss case

The `FLOW` boss case combines the four lesson concepts.

It should require the learner to identify at least:

- where work is accumulating;
- the likely system constraint;
- why local utilization may be misleading;
- which intervention should be attempted first.

V0 only needs the interaction shell and placeholder case content until the learning content phase begins.

## Deployment

Deploy static output with GitHub Actions to GitHub Pages.

Because `tim8es/pmo01` is currently private, Pages availability depends on the GitHub plan and repository settings. If private Pages is unavailable, the code remains deployable and can later be made public or hosted elsewhere without architecture changes.

## Validation and testing

V0 testing is intentionally narrow.

Required checks:

- Astro build succeeds.
- TypeScript checks succeed.
- Every lesson page renders.
- Previous/next navigation resolves correctly.
- Progress persists after reload in the same browser.
- Decision Drill can select and reveal an analysis.
- Mobile layout is readable at common narrow widths.
- Basic keyboard navigation works for interactive controls.

Do not build a large E2E suite before the learning format is validated.

## Explicit non-goals

V0 does not include:

- backend;
- database;
- authentication;
- cloud progress synchronization;
- analytics SDK;
- CMS;
- search;
- comments;
- social features;
- leaderboard;
- XP or virtual currency;
- generic gamification engine;
- generalized mastery engine;
- knowledge graph;
- personalized learning paths;
- AI tutor;
- full PM course content.

Any of these requires a separate design decision after the vertical slice is tested.

## Acceptance criteria

V0 is complete when:

1. GitHub Pages build/deployment configuration exists and the static site builds successfully.
2. The homepage presents the course as a typographic table of contents.
3. Four `FLOW` lesson routes exist and share one editorial lesson template.
4. A learner can move previous/next through the module.
5. A learner can mark lessons as studied and the state survives reload.
6. At least one Decision Drill demonstrates the intended interaction.
7. A module boss-case page demonstrates the final assessment format.
8. The experience is readable and usable on desktop and mobile.
9. No backend or unnecessary application framework is introduced.
10. Content can be replaced later without restructuring the page architecture.

## Post-V0 decision gate

Do not expand the platform immediately after implementation.

First evaluate:

- whether the editorial format supports sustained reading;
- whether Decision Drills produce useful reflection;
- whether the boss-case format exposes gaps in reasoning;
- what UI elements are actually missing;
- which architecture problems are real rather than hypothetical.

Only then decide whether to add mastery evidence, richer progress, prerequisites, MDX components, analytics, or additional course modules.
